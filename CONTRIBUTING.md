# Как вносить изменения

## Ветки и pull request

- Ветка `main` защищена: прямые push запрещены, изменения попадают только через pull request.
- Ветку называем по типу изменения: `feat/...`, `fix/...`, `chore/...`, `docs/...`, `test/...`.
- Каждый pull request содержит тесты на то, что он меняет.
- Слияние возможно только после зелёной проверки `ci`. Способ слияния один: squash.
- Заголовок pull request становится сообщением коммита в `main`, поэтому пишем его в формате Conventional Commits: `feat(api): add venue analytics`.

## Проверки перед push

Из каталога `backend`:

```bash
npm ci
npm run lint
npm run typecheck
npm test
```

`npm run format` приводит код к стилю Prettier.

Из каталога `frontend`:

```bash
npm ci
npm run lint
npm run typecheck
npm test
```

## Соглашения бэкенда

`backend/` - самостоятельный сервис на Node 24 и TypeScript: Fastify 5, zod 4, PostgreSQL 18. Перед тем как писать новый модуль, откройте соседний готовый (`src/http/routes/auth.ts`, `src/services/auth.ts`, `src/repositories/users.ts`) и повторите его устройство. Ниже собрано то, что проверяется на ревью.

### Язык и модули

- TypeScript в строгом режиме с `noUncheckedIndexedAccess` и `erasableSyntaxOnly`: без `enum`, `namespace` и параметров-свойств в конструкторах. Вместо `enum` используем массив `as const` и тип от него, как в `src/domain/vocabulary.ts`.
- ESM, импорты с расширением `.ts`: `import { x } from './y.ts'`. Типы импортируются через `import type`.

### Слои

| Каталог | Что в нём |
| --- | --- |
| `src/domain/` | доменные модели (`models.ts`), словари тегов и статусов (`vocabulary.ts`), чистые функции расчётов (`nutrition/`) |
| `src/repositories/` | только SQL |
| `src/services/` | бизнес-правила |
| `src/http/routes/` | тонкие HTTP-маршруты |
| `src/http/schemas/` | zod-схемы запросов и ответов, преобразование моделей в DTO |
| `src/ports/` | интерфейсы внешних систем (распознавание еды и меню, мессенджер, уведомления о бронях) |
| `src/shared/` | общие утилиты: ошибки, часы, время, геометрия, фоновые задачи |

- Репозиторий: функции принимают первым аргументом `db: Queryable` (это пул или клиент транзакции), перечисляют колонки явно, без `select *`. Строка таблицы описывается интерфейсом `XxxRow` в snake_case и превращается в модель в camelCase из `src/domain/models.ts`.
- Сервис: фабрика `createXxxService(deps)` возвращает интерфейс `XxxService`. Все зависимости (пул, часы, порты, настройки) передаются явно, глобальных объектов нет. Записи, которые должны пройти вместе, выполняются внутри `withTransaction(pool, fn)`, и репозитории получают клиент транзакции.
- Маршрут: разбирает запрос, вызывает сервис и возвращает DTO. SQL и бизнес-правил в маршрутах нет.
- Внешние системы подключаются через интерфейсы из `src/ports/`, реализации живут отдельно (например, `src/recognition/`). Так сервис тестируется с подменой, а без ключей внешнего API сервер всё равно запускается.

### Связывание зависимостей

Новый сервис:

1. Интерфейс и фабрика в `src/services/<имя>.ts`.
2. Поле в интерфейсе `Services` в `src/services/index.ts`.
3. Создание в `createServices` в `src/container.ts`: сюда передаются пул, часы, порты и нужные значения из конфигурации.
4. Заглушка по умолчанию в `fakeServices` в `test/services.ts`, которая отклоняет вызов (`Promise.reject(new Error('... is not stubbed'))`). Без неё перестанут компилироваться остальные тесты.

Новые маршруты:

1. Плагин в `src/http/routes/<имя>.ts`, который получает нужные сервисы через опции.
2. Регистрация в `apiRoutes` в `src/http/routes/index.ts`. Все маршруты API живут под префиксом `/api/v1`.
3. Тег в `API_TAGS` в `src/http/openapi.ts`, если подходящего ещё нет.

### Маршруты HTTP

- Плагин пишется в стиле `FastifyPluginCallbackZod<Options>` и заканчивается вызовом `done()`.
- В `schema` каждого маршрута обязательно:
  - `operationId`: уникальный, в lowerCamelCase, глагол и объект (`getDiaryDay`, `createDeal`). По нему генерируется клиент мини-приложения, поэтому переименование ломает фронтенд.
  - `tags`: ровно один тег из `API_TAGS`.
  - `summary` на русском.
  - `description` на русском, если у метода есть поведение или коды ошибок, о которых должен знать клиент. Перечислите значения `code` и что клиенту делать в каждом случае (пример в `src/http/routes/auth.ts`).
  - `response`: успешный ответ через `success('Описание', Schema)`, пустой через `204: noContent('Описание')`, и `...errorResponses(...)` со всеми статусами ошибок, которые метод действительно возвращает, из набора 400, 401, 403, 404, 409, 413, 415, 422, 503. Статусы 429 и 500 хелпер добавляет сам.
- Все ошибки отдаются в формате `application/problem+json` (RFC 9457). В коде бросаем `AppError` через хелперы из `src/shared/errors.ts`: `badRequest`, `unauthorized`, `forbidden`, `notFound`, `conflict`, `unprocessable`, `unavailable`. Поле `code` в snake_case - это контракт с клиентом, его не меняем без причины. `detail` пишется по-английски и не содержит внутренних подробностей: текстов SQL, стеков, ответов внешних сервисов. Невалидный ввод автоматически получает 400 с кодом `validation_failed`.
- Методы, требующие входа, объявляют `preValidation: requireAuth` и `security: bearerSecurity`. Именно `preValidation`, а не `preHandler`: так запрос без токена получает 401 раньше, чем 400 за невалидное тело. Идентификатор вызывающего берём через `userId(request)`.
- Дорогие методы (распознавание фото еды и разбор меню, загрузка файлов) получают собственный лимит, обычно `config: { rateLimit: { max: 20, timeWindow: '1 minute' } }`, для фото меню 10 в минуту. Общий лимит на всё API задаёт переменная `RATE_LIMIT_PER_MINUTE`.
- Фото принимаем через `readImageUpload(request)` из `src/http/uploads.ts`: он возвращает `{ data, mimeType }` и определяет тип по содержимому (JPEG, PNG, WebP). В маршруте нужны `config: { imageUpload: true }`, чтобы multipart попал в OpenAPI, и `...errorResponses(...IMAGE_UPLOAD_ERROR_STATUSES, ...)`.

### DTO и схемы

- Схемы ответов описываются на zod в `src/http/schemas/`. Переиспользуемые компоненты помечаются `.meta({ id: 'Name', description: '...' })`, неочевидные поля `.describe('...')`. Описания на русском: они попадают в документацию API.
- Даты в ответах - строки ISO 8601 в UTC: в схеме `IsoDateTime`, при преобразовании `iso()` и `isoOrNull()` из `src/http/schemas/common.ts`.
- Доменная модель наружу напрямую не отдаётся. Преобразование делает функция `toXxx()` в модуле схемы, как `toUserProfile` в `src/http/schemas/users.ts`.
- Входные схемы строгие: границы чисел, длины строк, перечисления. Плохой ввод должен отсекаться на валидации с ответом 400, а не падать в сервисе. Для параметра `:id` есть готовая схема `IdParams`.

### Время

- Текущий момент берётся только из `Clock` (`src/shared/clock.ts`), который сервис получает в зависимостях. `new Date()` без аргументов и `Date.now()` в бизнес-логике не используем: тесты подставляют `fixedClock` из `test/clock.ts` и управляют временем через `set` и `advance`.
- Календарные дни, слоты приёма пищи и часы работы заведения считаются в часовом поясе пользователя или заведения через `src/shared/time.ts` (`localDate`, `dayRange`, `addDays`, `isOpenAt`), а не в поясе сервера.

### База данных

- Схема меняется только новой миграцией `backend/migrations/NNNN_<имя>.sql` со следующим номером по порядку. Уже применённые миграции не редактируются: при запуске сверяется контрольная сумма, и изменённый файл остановит сервис с ошибкой. Миграция с номером меньше последней применённой тоже будет отклонена.
- Миграции применяются при старте сервиса (`MIGRATE_ON_START=true`) и перед интеграционными тестами.
- Запросы только параметризованные (`$1`, `$2`, ...), значения не вклеиваются в текст SQL.
- Хелперы из `src/db/pool.ts`: `one` (ровно одна строка), `maybeOne` (строка или `null`), `withTransaction`, `jsonb()`. Запись в колонку `jsonb`: в SQL `$n::jsonb`, в параметрах `jsonb(value)`.
- Что возвращает драйвер: `bigint` и `numeric` приходят числами (значение за пределами безопасного целого вызывает ошибку), `double precision` числом, `timestamptz` объектом `Date`, `time` строкой `'HH:MM:SS'`, `text[]` массивом, `jsonb` уже разобранным значением.

### Тесты

- Модульные тесты `*.test.ts` лежат рядом с кодом и не обращаются к базе. Интеграционные `*.int.test.ts` работают с настоящим PostgreSQL и выполняются последовательно. По отдельности их запускают `npm run test:unit` и `npm run test:integration`.
- Сервисы и репозитории проверяются интеграционными тестами: `testPool()`, `resetDatabase()` перед каждым тестом и `closeTestPool()` в конце из `test/database.ts`.
- HTTP-маршруты проверяются на подменах, без базы: `buildTestApp({ services: { ... } })` из `test/services.ts`, запросы через `app.inject`, заголовок авторизации через `bearer('guest-token')`. Готовые токены в `TEST_TOKENS`: `guest-token` (пользователь 101), `venue-token` (202), `demo-guest-token` (демо-гость -1001).
- Каждый ответ, который проверяет тест маршрута, проходит через `expectContract(response, 'GET', '/api/v1/...')` из `test/contract.ts`. Хелпер сверяет статус, тип содержимого и тело с закоммиченным `openapi.yaml`.
- `openapi.yaml` в корне репозитория генерируется из кода. После любого изменения маршрутов или схем выполните `npm run openapi` в `backend/` и закоммитьте результат, причём до запуска тестов маршрутов, иначе `expectContract` сверит ответы со старым контрактом. `src/http/openapi.test.ts` падает, если файл разошёлся с кодом, и дополнительно проверяет уникальность `operationId`, problem+json на всех ошибках, 401 на защищённых методах и 400, 413, 415 на загрузках.
- Прочие хелперы: `multipart` и `TINY_PNG` (`test/multipart.ts`) для загрузок, `signInitData` и `maxUserJson` (`test/init-data.ts`) для входа через MAX.
- Демо-учётки используют отрицательные id (`DEMO_ACCOUNTS` в `src/auth/demo.ts`), обычным пользователям в тестах даём положительные.

### Локальное окружение

```bash
cp .env.example .env
docker compose up -d --wait db
cd backend
npm ci
npm test
npm run dev
```

- База поднимается в Docker и слушает только `127.0.0.1:55432`, пользователь и пароль `ppshkin`.
- Тесты берут адрес базы из `TEST_DATABASE_URL`, по умолчанию `postgres://ppshkin:ppshkin@127.0.0.1:55432/ppshkin_test`. Имя базы обязано заканчиваться на `_test`: подготовка тестов пересоздаёт схему `public`, и проверка имени защищает рабочую базу. Саму базу подготовка создаёт, если её нет. Чтобы два одновременных прогона не мешали друг другу, дайте каждому свою базу, например `ppshkin_menu_test`.
- Если локальный npm падает при установке (так ведёт себя npm 11.2 на peer-зависимостях vitest), используйте зафиксированную версию: `npx -y npm@11.19.0 ci` и `npx -y npm@11.19.0 install --save-exact <пакет>@<версия>` из `backend/`.
- Перед push, кроме проверок из раздела выше, выполните `npm run build`, а при изменении маршрутов ещё и `npm run openapi`. CI повторяет эти шаги, считает покрытие и собирает Docker-образ.

### Оформление

- Комментариев нет ни в одном файле: TypeScript, SQL, YAML, JSON, Dockerfile, shell. Если без комментария непонятно, переименуйте или разбейте код.
- Длинные тире (символы U+2014 и U+2013) не используются нигде: в коде, текстах бота, документации, названиях тестов, коммитах и описаниях pull request. Вместо них обычный дефис `-` или другая формулировка.
- Без `TODO` и `FIXME`, мёртвого кода, неиспользуемых экспортов и зависимостей, временных файлов.
- Зависимость добавляется, только когда без неё не обойтись, и всегда с точной версией (`save-exact` уже включён в `backend/.npmrc`). `package-lock.json` коммитится.
- Секреты (токен бота, `SESSION_SECRET`, ключи внешних API) хранятся только в `.env` и в секретах GitHub Actions и никогда не печатаются в логи. Новая переменная окружения добавляется в схему `src/config.ts` и в `.env.example` с пустым или безопасным значением.
- Коммиты в формате Conventional Commits на английском. Тексты для пользователей и документация на русском, `detail` в ошибках API и сообщения логов на английском.
