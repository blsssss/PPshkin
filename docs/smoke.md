# Живые проверки и чек-лист перед сдачей

Модульные и интеграционные тесты работают на подделках и не видят проблем рабочей среды: истёкший сертификат, отписанный webhook, закончившийся баланс ChadGPT, расхождение рабочего API с [DATA-API.yaml](../DATA-API.yaml). Поэтому перед сдачей и после изменений на сервере выполняются две вещи:

1. живые проверки `npm run smoke`: скрипт обращается к настоящим MAX Bot API, ChadGPT и развёрнутому сервису;
2. ручной чек-лист основного сценария в веб-версии MAX, на Android и на iOS.

Живые проверки запускаются только вручную. В обычном CI и в тестах их нет: там только подделки, без сети и настоящих ключей. Когда запускать и как запустить workflow, описано в конце документа.

## Живые проверки

| Проверка | Что делает | Успех | Переменные |
|---|---|---|---|
| `max.me` | `getMe()` клиента MAX Bot API | ответ получен по TLS с сертификатом Минцифры, `username` равен `MAX_BOT_USERNAME` | `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`, `MAX_API_BASE_URL` (по умолчанию `https://platform-api2.max.ru`) |
| `max.webhook` | `listSubscriptions()` | есть подписка на `${PUBLIC_BASE_URL}/max/webhook` с типами `bot_started`, `message_created`, `message_callback`, `bot_stopped` | `MAX_BOT_TOKEN`, `PUBLIC_BASE_URL` |
| `site.health` | `GET /health` и `GET /ready` | оба 200, сертификат валиден | `PUBLIC_BASE_URL` |
| `site.miniapp` | `GET /` | 200, `text/html`, в HTML подключён `https://st.max.ru/js/max-web-app.js` | `PUBLIC_BASE_URL` |
| `site.docs` | `GET /docs/json` | 200, документ OpenAPI 3 с той же `info.version`, что в [openapi.yaml](../openapi.yaml) | `PUBLIC_BASE_URL` |
| `recognition.photo` | распознавание фото [dish.jpg](../backend/testdata/samples/dish.jpg) | `status: recognized`, хотя бы одно блюдо, у каждого `0 < kcalMin <= kcalMax <= 2000`, ответ не дольше 45 секунд; в деталях ответившая модель, время ответа, блюда и диапазон калорий | `CHADGPT_API_KEY`, `CHADGPT_BASE_URL`, `CHADGPT_MODEL`, `CHADGPT_FALLBACK_MODEL`, `CHADGPT_TIMEOUT_MS` |
| `recognition.text` | оценка текста «капучино и круассан» | `status: recognized`, хотя бы одно блюдо, ответила модель ChadGPT | `CHADGPT_API_KEY` |
| `recognition.menu` | разбор меню [menu.txt](../backend/testdata/samples/menu.txt) | `status: parsed`, не меньше 4 позиций с ценой, ответила модель ChadGPT | `CHADGPT_API_KEY`, `CHADGPT_MENU_TIMEOUT_MS` |
| `api.<id>` | каждая проверка из [DATA-API.yaml](../DATA-API.yaml) против `PUBLIC_BASE_URL` | статус входит в `expect`, тип содержимого совпадает, все `requiredFields` есть в теле (точечные пути, `[]` проверяет каждый элемент массива) | `PUBLIC_BASE_URL`, для ролей `guest` и `venue` ещё `DEMO_GUEST_TOKEN` или `DEMO_VENUE_TOKEN` |

Значения `CHADGPT_*` и `MAX_API_BASE_URL` по умолчанию те же, что у backend (`backend/src/config.ts`).

Правила:

- Проверка без нужной переменной окружения получает `skipped`, а с `--strict` (так запускает workflow) `failed`; в деталях названа недостающая переменная. Без `CHADGPT_API_KEY` распознавание пропускается, а не переключается на локальный справочник.
- Если ChadGPT не ответил, распознавание оценивает текст по локальному справочнику (модель `reference`), а меню разбирает эвристикой (модель `text-heuristic`). Для живой проверки это `failed`: в деталях `ChadGPT did not answer, the offline ... did`.
- Проверки `site` и `max.me` требуют адрес `https://` (`PUBLIC_BASE_URL`, `MAX_API_BASE_URL`) и включённую проверку сертификатов. С адресом `http://` или с `NODE_TLS_REJECT_UNAUTHORIZED=0` они получают `failed`: валидность сертификата тогда не подтверждена. Проверки `api` принимают `http://` только для `localhost`, `127.0.0.1` и `[::1]`: так [DATA-API.yaml](../DATA-API.yaml) можно прогнать на локальном стенде (`PUBLIC_BASE_URL=http://localhost:3000` и локальные демо-токены), а демо-токены не уходят по сети в открытом виде.
- Сертификат `platform-api2.max.ru` выдан удостоверяющим центром Минцифры, поэтому для проверок MAX нужен `NODE_EXTRA_CA_CERTS` с путём к `backend/certs/russian_trusted_root_ca.pem`. Без него запрос падает с `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`, и `max.me` пишет об этом в деталях.
- Проверки MAX только читают. `subscribe`, `unsubscribe` и `getUpdates` не вызываются: long polling удаляет подписку webhook рабочего бота, а при активной подписке и не работает.
- Проверки `api` выполняют запросы из [DATA-API.yaml](../DATA-API.yaml) с их побочными эффектами: приём пищи демо-гостя и бронь в «Пенке», которая истекает через 60 минут. Это допустимо, демо-данные пересоздаются ежедневно. Запросы идут по одному, перенаправления не выполняются: ответ 308 считается ошибкой.
- Каждый запрос к сайту и API ждёт ответа не дольше 20 секунд, весь прогон ограничен 12 минутами. Когда время прогона вышло, незавершённые запросы прерываются, а оставшиеся проверки получают `failed` с `not started, the run reached its 12 min limit`. Так отчёт попадает в Summary раньше, чем workflow остановится по `timeout-minutes: 15`.
- Ни токены, ни ключи, ни `initData`, ни данные пользователей не попадают в отчёт и в вывод. Тела ответов в отчёт не пишутся, только статус, тип содержимого и пути недостающих полей. Последним шагом значения `MAX_BOT_TOKEN`, `CHADGPT_API_KEY`, `DEMO_GUEST_TOKEN` и `DEMO_VENUE_TOKEN` заменяются в отчёте на `[redacted]`.

Отчёт: Markdown-таблица `| Проверка | Результат | Время | Детали |` с результатами `ok`, `failed`, `skipped` и строкой «Итого». Он печатается в stdout и дописывается в файл `GITHUB_STEP_SUMMARY`, если переменная задана. Код выхода 1, если есть `failed`, и 2 при неверных аргументах.

Стоимость: один полный прогон распознавания (три запроса: фото, текст, меню) стоит около 0,05-0,2 ₽ баланса ChadGPT; при сбое или неверном ответе распознавание повторяет запрос (после двух неверных ответов к запасной модели), и каждый повтор тоже расходует баланс. Проверка `api.guest-meal-text` вызывает ChadGPT на сервере и расходует ещё один текстовый запрос. Проверки `max` и `site` бесплатны, для частых повторов используйте `--checks max,site`.

### Локальный запуск

Из каталога `backend/`. Скрипт читает `.env` из корня репозитория (`--env-file-if-exists=../.env`), поэтому в нём должны быть те же переменные, что и в workflow (раздел «Запуск в GitHub Actions»), включая `MAX_BOT_USERNAME`. Демо-токены `local-demo-...` из `.env.example` подходят только для локального стенда, рабочий сервер ответит на них 401.

```bash
NODE_EXTRA_CA_CERTS=certs/russian_trusted_root_ca.pem npm run smoke -- --checks max,site
npm run smoke -- --checks recognition
NODE_EXTRA_CA_CERTS=certs/russian_trusted_root_ca.pem npm run smoke -- --checks all --strict
```

Аргументы: `--checks` со списком через запятую из `max`, `site`, `recognition`, `api` или `all` (по умолчанию `all`) и `--strict`.

## Когда запускать

Живые проверки и чек-лист:

- перед сдачей работы;
- после каждого деплоя (обновление по разделу 9 [deploy.md](deploy.md));
- после смены токенов, ключей и переменных: `MAX_BOT_TOKEN`, `CHADGPT_API_KEY`, `DEMO_GUEST_TOKEN`, `DEMO_VENUE_TOKEN`, `PUBLIC_BASE_URL`, `MAX_BOT_USERNAME`.

## Запуск в GitHub Actions

Workflow [smoke.yml](../.github/workflows/smoke.yml) запускается только вручную: Actions, smoke, Run workflow, в поле `checks` выбрать `all`, `max`, `site`, `recognition` или `api`. Из терминала:

```bash
gh workflow run smoke.yml -f checks=all
gh run watch
```

Таблица результатов появляется в Summary запуска. Workflow всегда работает с `--strict`, поэтому незаданный секрет или переменная дают `failed`. `NODE_EXTRA_CA_CERTS` workflow задаёт сам.

Секреты и переменные репозитория (Settings, Secrets and variables, Actions):

| Имя | Вкладка | Значение | Для каких проверок |
|---|---|---|---|
| `MAX_BOT_TOKEN` | Secrets | токен рабочего бота | `max` |
| `CHADGPT_API_KEY` | Secrets | ключ ChadGPT с положительным балансом | `recognition` |
| `DEMO_GUEST_TOKEN` | Secrets | значение `DEMO_GUEST_TOKEN` из `.env` сервера | `api` |
| `DEMO_VENUE_TOKEN` | Secrets | значение `DEMO_VENUE_TOKEN` из `.env` сервера | `api` |
| `PUBLIC_BASE_URL` | Variables | `https://hackathon.easymythic.dev` | `max`, `site`, `api` |
| `MAX_BOT_USERNAME` | Variables | ник бота без `@`, для рабочего бота `t516_hakaton_max_bot` | `max` |
